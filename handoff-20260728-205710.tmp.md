## NEW MANDATE: the plugin interface (task #17, in_progress)

Alan's words, near verbatim: adding a new plugin should be very easy. Steps and the plugin
interface should be one thing. He should be able to see a plugin in one file. Right now
things happen across files that are implied. A plugin should be a deep and constrained
interface.

The verified current wiring, which is what he is reacting to. A plugin today is a naming
convention over four files joined by the string `${plugin.type}/${action.slug}`:

1. `packages/plugins/src/<name>/index.ts` declares browser-safe metadata
   (`IntegrationPlugin`: type, label, formFields, actions with slug/configFields/output
   schema) and calls `registerIntegration()` as an import side effect into
   `packages/shared/src/plugins/registry.ts`.
2. `packages/plugins/src/<name>/steps/<action>.ts` builds the implementation with
   `defineStep({ id: "type/slug", input, output, handler })`.
3. `packages/plugins/src/server.ts` joins them: `registerStep("type/slug", lazyImport)`
   into `packages/core/src/backend/lib/step-registry.ts` (`STEP_LOADERS`), imported by the
   server for its side effects. Connection tests register there too, joined on the bare
   plugin-type string via `registerIntegrationTest`.
4. `packages/plugins/src/<name>/schemas.ts` holds the schemas both sides import.

Compile-time checks that exist: `registerStep`'s id must equal the step's declared id
(the `NoInfer` signature at `step-registry.ts:135`), and the handler's parameter and
return types derive from the schemas. Everything else is convention: nothing proves a
declared action has a registered step, nothing ties a step id to any declared type/slug
pair, the `IntegrationType` union in `packages/shared/src/types/integration.ts` is
hand-kept, and `packages/plugins/src/index.ts` is a hand-kept import list. Failures
surface at run time inside a workflow. The assessment delivered to Alan named the red
flags in Ousterhout's terms: information leakage, change amplification (the
`packages/plugins/src/AGENTS.md` quick-start is literally a checklist of files to touch),
conjoined modules, and registration by import side effect.

What is already good and should survive: `defineStep` itself is a deep module (owns the
config decode, the credential fetch, the run log, the `StepResult` envelope), and the
`client.ts`-over-`callVendor` layering in `vendor-http.ts`.

The real constraint any design must satisfy: the browser/server split. The editor loads
plugin metadata into the browser and derives template autocomplete from output schemas at
registration; vendor code must stay out of the browser bundle and lazy on the server.
"One file" collides with that unless the design resolves it deliberately (lazy per-action
loaders in a single manifest, a per-plugin server entry beside a browser entry, or
something better). Other constraints: `@rova/plugins` builds against `@rova/core/plugin`
and nothing else; outputs stay JSON-safe (Inngest memoization); registration refuses an
underivable output schema; no backwards compatibility, old surfaces may die; the README
documents the surface for outside plugin authors.

Sequencing note: `step-registry.ts:37` already says stage 7 turns `STEP_LOADERS` into a
service the engine reads inside the app runtime. The registry gets rebuilt in stage 7
anyway, so the plugin-seam redesign and stage 7 should be sequenced together deliberately
rather than as two migrations touching the same module. Design gate first in either case:
two genuinely different interface shapes, compared, one recommended, Alan approves before
implementation.

**Stage 7: the workflow-engine interior.** Scope unchanged from the prior handoff:

1. Kill the `globalThis`-backed `db` proxy and `getDb`
   (`packages/core/src/backend/lib/db/index.ts`); the step store, step logger, credential

   them across is what lets the proxy die. `callDbModule` is the seam;

2. Kill the module-level Inngest client (`lib/inngest/client.ts`); `InngestClientLayer`
   delegates to `runtime-events.ts` which reaches `getInngestClient()`.
3. Remove the Promise seam inside `defineStep` (`withStepLogging`, `fetchCredentials`,
   `Effect.runPromise`); an author's handler does not change.
4. Remove `toPlainLogger` in `services/workflows/triggering/routing.ts`.
5. Decide the two built-in steps (`Database Query`, `HTTP Request`), whose flat shapes
   `registerBuiltInStep` exists for; converting them is a template-surface decision and
   closes issue #13 by construction. Alan decides.
6. Own the Inngest function registry's module-level cache (`lib/inngest/functions.ts`).

Constraints: Inngest stays the durable substrate (ADR-0004); node outputs JSON-safe;

wrapper; keep the four-member `WorkflowExecutionRuntime` seam. Scout first: one agent

foundation and pilot, review, fix, commit, then sweep. When the engine lands: verify

sequencing section done.
